# Graph-workflow relevance


## Graphs that make specific workflows useful

Some workflows/queries are only useful when a specific graph is applied, like how the workflow 'connect problems/solutions' is only useful when applied in a graph where the 'solution is already identified', meaning the solution is a 'node or connection (or sequence/combination/structure of nodes/connections)' on the graph, and the 'position of the solution node/connection' is already identified, so progress toward the intent of 'connecting the problem/solution' can be measured.

In a graph where only problem structures/positions are known, like a graph of related problems or problem types, the 'solution position/structure' can be identified by:
- applying 'combinations/sequences/structures of interface variables' surrounding problems until 'overlaps/intersections/alignments/similarities with solution structures' are generated
- applying changes to common/probable problem variables like 'complexity/volatility/imbalance' until solution structures are generated
- applying changes to what is known about the solution, like general solution metrics like 'accuracy', until a 'position/structure on the problem graph' is generated


## Graphs that make general workflows useful

Some graphs can make any query useful, like graphs that trivially connect every set of nodes.


## Queries useful on any graph

Some queries can be useful on any graph, usually general queries like 'find adjacent hubs' to 'find important nodes like type/abstract nodes', which is a generally useful query because most graphs have hub nodes.


## Graphs implementing workflows

Some graphs implement a workflow like "apply a similarity to solve a problem like a 'comparison'", such as a graph that applies a 'type' similarity to 'identify the problem type', to solve/simplify the problem of 'matching/comparing the problem with a solution type'. 

This workflow is a variant of the workflow to 'identify the position/structure of the problem in a problem definition, and apply an opposing function of the problem', like identifying whether the problem is a 'function/description/object' in the problem/definition, and then identifying the opposing structure of that 'function/description/object', which is useful with a slightly different graph of 'opposing matched specific problem/solution sets', rather than 'opposing matched problem/solution types'.


## Queries useful on a graph, as indicated by graph structure

The structure of the graph indicates what queries will be useful on the graph, like how a 'graph of problem types surrounded by specific problems and solution types surrounded by specific solutions and matched opposing problem/solution types' has useful queries like 'identify problem/solution type of a specific problem/solution' and 'identify opposing problem/solution type' which are 'different types of adjacent connections' on this graph, so a workflow could be generated by 'sequencing/composing these queries' like 'identify general type, then identify opposing type'.
